# Confirm gate — подтверждение операций в Telegram

Гейт удерживает изменяющий вызов к сторонней интеграции и пропускает его только
после того, как оператор нажал кнопку в Telegram.

## Зачем

Агенты запускаются с `claude --dangerously-skip-permissions`
(`agent-architecture/orchestration/session-exec.sh`). Это выключает штатный слой
разрешений целиком: блок `permissions.allow` / `permissions.deny` из
`settings.json` не действует. Hooks — единственный барьер, который переживает
этот флаг.

Целевой класс — бизнес-интеграции, которые подключает пользователь: 1С, amoCRM,
Bitrix24, Teamly, Yandex Tracker, Yandex Disk, HH.ru и любые последующие.

## Что гейтится

| Форма вызова | Как ловится |
|---|---|
| MCP-инструмент | глагол в имени: `mcp__amocrm__delete_lead` → `delete` |
| Обобщённый HTTP-инструмент | поле `tool_input.method` |
| `Bash` с `curl` | глагол в URL, затем HTTP-метод из команды (`-X DELETE`, `-XDELETE`, `-d`, `-d@file`, `-F`, `-T`) |
| `Bash` прочее | только явные `confirm_patterns` из политики |

## Что НЕ гейтится

Гейт видит только `mcp__*` и `Bash`. Все встроенные инструменты сессии проходят
молча — это локальные операции, а не бизнес-данные:

`Read`, `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, `Glob`, `Grep`, `Task`,
`TodoWrite`, `WebFetch`, `WebSearch`, `Skill`, `SlashCommand`, `AskUserQuestion`.

Обычные команды `Bash` тоже: `git status`, `git commit`, `npm install`, `ls`,
`cat`, `pytest`, `docker ps`, `rm /tmp/x`, `curl` без изменяющего метода и без
изменяющего глагола в URL.

Проверка области действия стоит ДО таблицы глаголов намеренно. Имена встроенных
инструментов сталкиваются с ней лоб в лоб: `Write`, `Edit`, `TodoWrite` несут
изменяющие глаголы, а `Glob`, `Grep`, `Task` не содержат известного глагола
вовсе и попали бы в ветку «неизвестный → спросить». Гейт, дёргающий оператора в
каждой сессии, будет выключен за день и не защитит ничего.

Единственное исключение — запись в саму конфигурацию гейта: `Write`/`Edit` по
пути с `confirm-policy.yaml` или `settings.json` требует подтверждения.
Совпадение идёт по сегменту пути, а не по подстроке: `settings.json.bak` и
`src/settings.jsonc` — другие файлы и не дёргают клиента.

### Почему не по HTTP-методу

На уровне PreToolUse-хука метода не видно: хук получает только `tool_name` и
`tool_input`, а запрос `DELETE /v3/deals/42` выполняет MCP-сервер уже после того,
как хук пропустил вызов.

Там, где метод виден (команда `Bash`), одного его всё равно мало. Bitrix24
выполняет разрушающие операции через GET:

```
https://portal.bitrix24.ru/rest/1/<token>/crm.deal.delete?ID=1
```

Метод GET, сделка удаляется. 1С с самописными HTTP-сервисами ведёт себя так же.
Поэтому для `Bash` глагол ищется ещё и в URL — токен `delete` даёт подтверждение
независимо от метода.

Глагол ищется не во всей команде и не во всём URL, а только в «операционной»
части адреса — путь, query, фрагмент:

* по всей команде прогон поймал бы `git add` на глаголе `add`;
* схема и хост отброшены — глагол в домене (`update.example.com`) это имя, а не
  операция;
* URL, оканчивающийся расширением файла (`.sh`, `.zip`, `.json`, `.pdf` и
  подобные), считается скачиванием и из правила исключается — иначе
  `curl .../main/update.sh` и `wget .../archive/dataset.zip` дёргали бы клиента
  на обычной работе. Плата за это: API в стиле `/api/deals/delete.json` правилом
  по URL не ловится, остаётся HTTP-метод и `confirm_patterns`.

## Порядок правил

Первое совпадение выигрывает:

1. `mode: off` → сквозной пропуск
2. `overrides.deny` → блок без вопроса
3. `overrides.allow` → пропуск молча
3a. не `mcp__*` и не `Bash` → пропуск молча (кроме правки конфигурации гейта)
4. `tool_input.method` → по таблице HTTP-методов. Это поле умеет только
   **повысить** строгость: `delete_deal`, вызванный с `{method: "GET"}`, всё
   равно судится по глаголу. Иначе гейт отключался бы одним лишним аргументом
5. `Bash` → глагол в URL, HTTP-метод, `confirm_patterns`
6. глагол в имени инструмента → `read` пропускаем, остальное спрашиваем
7. **глагол неизвестен → спрашиваем**

Пункт 7 — сердце гейта. Подключили новый MCP-сервер с незнакомым инструментом —
он спросит, а не проскочит. Правку политики при этом делать не нужно.

## Fail-closed

| Ситуация | Поведение |
|---|---|
| Политика не читается или не парсится | deny |
| `CONFIRM_POLICY_PATH` не задан, но канал есть | deny (роут отдаёт 503) |
| Канала нет вовсе (ни URL, ни порта) | **passthrough** — см. ниже |
| Плагин недоступен, вызов гейтится | deny |
| Плагин недоступен, вызов обычный | **пропуск** — см. ниже |
| Карточку некому доставить | deny сразу, без ожидания таймаута |
| Оператор молчит 5 минут | deny |
| Оператор нажал «Отклонить» | deny |
| Глагол неизвестен | **спрашиваем**, не deny |

Это осознанное отличие от `ask-user-question-hook.ts`, который при недоступном
плагине деградирует к нативному терминальному UI. Гейт, который открывается при
поломке, — не гейт.

### Хук классифицирует до того, как звонит

Матчер хука — `*`, через него проходит каждый вызов инструмента. Поэтому
классификация живёт в самом хуке, а не только на сервере: он читает ту же
политику тем же кодом и отвечает локально.

| Что решил хук локально | Плагин доступен | Плагин лежит |
|---|---|---|
| обычный вызов (`local-tool`, `plain-bash`, читающий глагол) | пропуск, сеть не трогается | пропуск |
| пропуск по политике (`overrides.allow`, `mode: off`) | спрашивает плагин → аудит | пропуск |
| всё остальное | спрашивает плагин → карточка | **deny** |

Без этого рестарт плагина блокировал бы `Read`, `Grep`, `ls` — то есть
обычную работу сессии, которую гейт всё равно пропустил бы. Fail-closed
должен защищать бизнес-данные, а не останавливать агента, когда моргнул его
собственный канал. Отказать по недоступности плагина может только вызов,
который и так шёл на подтверждение.

Побочный эффект — цена: HTTP-запрос на каждый `Read` исчез. Накладные расходы
хука на обычном вызове ~65 мс, сеть не участвует.

Ровно одна ветка ведёт себя иначе, и она про **установку**, а не про работу:
если в окружении нет ни `CONFIRM_WEBHOOK_URL`, ни `TELEGRAM_WEBHOOK_PORT`, канала
не существует и спрашивать физически некого — хук пропускает вызов. Иначе хук,
прописанный в воркспейсе без плагина, заблокировал бы агента целиком. Как только
канал появился, любой сбой снова означает отказ.

## Установка

1. Скопировать `examples/confirm-policy.example.yaml` в
   `~/.claude-lab/<agent>/.claude/confirm-policy.yaml` и поправить под себя.
2. Задать в окружении сессии агента (systemd `EnvironmentFile` или wrapper):
   ```
   CONFIRM_POLICY_PATH=/home/<user>/.claude-lab/<agent>/.claude/confirm-policy.yaml
   TELEGRAM_WEBHOOK_TOKEN=<bearer плагина>
   ```
3. Влить блок `hooks` из `examples/settings.confirm-gate.example.json` в
   `~/.claude-lab/<agent>/.claude/settings.json` (не в `settings.local.json`).
4. Перезапустить сессию агента — hooks читаются только при старте.

**Агентам, созданным через `install.sh` / `new-agent.sh`, ничего из этого делать
не нужно** — политика кладётся в воркспейс, `CONFIRM_POLICY_PATH` попадает в
`channel.env`, а хук уже прописан в `settings.json.template`. Инструкция выше —
для агентов, созданных до появления гейта.

URL роута хук собирает сам из `TELEGRAM_WEBHOOK_HOST` / `TELEGRAM_WEBHOOK_PORT`,
которые уже лежат в `channel.env`. Порт в `settings.json` не зашивается: он
выбирается позже, чем рендерится шаблон, и меняется при переезде агента.
Переопределить можно через `CONFIRM_WEBHOOK_URL`.

Подтверждать может любой из `permission_relay.allowed_user_ids`; нажатия от
остальных отбиваются с «Не авторизован».

## Проверка после установки

```bash
# 1. читающий вызов проходит молча
curl https://api.hh.ru/vacancies/list

# 2. срабатывание по методу
curl -X DELETE https://example.invalid/x

# 3. срабатывание по глаголу в URL — метод GET, карточка обязана прийти
curl 'https://example.invalid/rest/1/tok/crm.deal.delete?ID=1'
```

При подключении каждой новой бизнес-интеграции прогнать по ней пункты 2-3 до
того, как агент получит к ней боевой доступ.

При старте плагин проверяет политику и пишет в лог `confirm gate armed` с
режимом — либо `confirm policy unreadable at startup`, если путь задан, но файл
не читается. Второе означает, что гейт будет отказывать во всём: опечатка в
`CONFIRM_POLICY_PATH` видна сразу, а не с первого делового вызова.

## Как добавить исключение

В `overrides.allow` политики, глобом по имени инструмента:

```yaml
overrides:
  allow:
    - "mcp__amocrm__list_*"
```

Целую бизнес-интеграцию в исключения не выносить. Смысл гейта именно в них.

## Как выключить

```
CONFIRM_GATE=off
```

в окружении сессии, затем рестарт. Либо `mode: off` в политике.

Только точное слово `off` отключает гейт: `0`, `no`, `false` не считаются — опечатка
не должна бесшумно снимать защиту.

## Аудит

Строкой в `logs/permissions.jsonl` с полем `"gate": "confirm"` пишутся: все
отказы, все ответы оператора и те пропуски, которые породило решение политики
(`overrides.allow`, `mode: off`).

Рядовой пропуск — локальный инструмент, обычная команда, читающий вызов — не
пишется намеренно. Матчер хука `*`, то есть через гейт проходит каждый вызов
инструмента; логируя все, файл превратился бы в стенограмму сессии, и реальные
вердикты в нём утонули бы.

## Граница защиты

Гейт защищает от ошибок агента, а не от агента-противника. У агента есть полный
`Bash`, и технически он может переписать файл политики. Смягчение: правки
`confirm-policy.yaml` и `settings.json` внесены в `confirm_patterns`, то есть сами
требуют подтверждения. Полной защиты от намеренного обхода на этом уровне нет.

Второй остаточный риск — инструмент с врущим именем: `get_report`, который внутри
что-то меняет. Снаружи видно только имя и аргументы. Смягчение: кнопка
«Подробнее» показывает аргументы вызова целиком, плюс точечные `overrides.deny`
по мере обнаружения таких инструментов.
