# Confirm Gate — Spec

**Дата:** 2026-09-08
**Статус:** согласовано с оператором, к реализации

## Проблема

Агенты запускаются с `claude --dangerously-skip-permissions`
(`agent-architecture/orchestration/session-exec.sh:42`). Это выключает штатный слой
разрешений целиком: блок `permissions.allow` / `permissions.deny` из
`agent-template/templates/settings.json.template` не действует.

Permission relay в `tg-plugin/plugin/src/channel/permissions.ts` реализован полностью
(карточка с `Allow`/`Deny`/`See more`, вердикт обратно в Claude Code, аудит в jsonl), но
питается уведомлением `notifications/claude/channel/permission_request`, которого CLI под
skip-permissions не шлёт. Механизм простаивает.

PreToolUse у основного агента содержит только `heartbeat-hook.sh`. Существующий гейт
`tg-plugin/plugin/src/chats/hooks/pre-tool-use.sh` работает лишь в multichat-сессиях
(выходит с `exit 0` без `MULTICHAT_STATE_DIR`) и умеет только блокировать, не спрашивать.

**Итог:** изменяющий вызов к любому стороннему сервису проходит без подтверждения.
Hooks — единственный барьер, который переживает `--dangerously-skip-permissions`.

## Цель

PreToolUse-хук, который удерживает изменяющий вызов, показывает оператору карточку в
Telegram с кнопками и пропускает вызов только после явного подтверждения.

## Целевой класс: бизнес-интеграции клиента

Защищать нужно то, что подключает пользователь: 1С, amoCRM, Bitrix24, Teamly,
Yandex Tracker, Yandex Disk, HH.ru и любые последующие. Они приходят в двух формах, и
обе обязаны быть под гейтом:

1. **MCP-сервер** — вызов вида `mcp__amocrm__delete_lead`.
2. **Голый REST через `Bash`** — 1С, HH.ru, Yandex Disk часто идут без MCP, агент бьёт
   в API напрямую через `curl`. Это не краевой случай, а основной путь.

Собственная инфраструктура (`second_brain` / `gbrain`) под гейт не попадает — решение
оператора. `firecrawl` тоже вынесен в исключения: читающая утилита, его глаголы
(`scrape`/`crawl`/`map`/`extract`) отсутствуют в таблицах и иначе спрашивали бы на каждом
вызове. Бизнес-интеграции в исключения не попадают никогда по умолчанию.

## Ключевое решение: классификация по глаголу, не по HTTP-методу

HTTP-метод на уровне хука невидим. PreToolUse получает только `tool_name` и `tool_input`
(видно в `chats/hooks/pre-tool-use.sh`); сам запрос `DELETE /v3/deals/42` выполняет
MCP-сервер уже после того, как хук пропустил вызов.

Метод виден в двух случаях, и оба используются:
1. `tool_input.method` — у обобщённых HTTP-инструментов (`fetch`, `request`).
2. Строка команды `Bash` — `curl -X DELETE`, `--request PATCH`, `-d` без `-X`.

Во всех остальных случаях инвариант — **глагол**. Он присутствует у любого MCP-сервера и
не зависит от вендора: `automations_delete`, `notion-update-page`, `send_message`,
`knowledge_base_bulk_delete`.

### Почему одного HTTP-метода недостаточно

Бизнес-API не соблюдают семантику REST. Bitrix24 выполняет разрушающие операции через
GET: `https://portal.bitrix24.ru/rest/1/<token>/crm.deal.delete?ID=1` — метод GET, сделка
удаляется. 1С с самописными HTTP-сервисами ведёт себя так же. Правило «GET безопасен» на
этом классе интеграций ложное.

Поэтому для `Bash` тот же токенайзер глаголов прогоняется **по URL из команды**:
`crm.deal.delete` даёт токен `delete` → подтверждение, независимо от метода. Токенайзер
применяется только к подстрокам, похожим на URL (содержат `://`), а не ко всей команде —
иначе `git add` попал бы под глагол `add` и оператор утонул бы в подтверждениях.

## Порядок применения (первое совпадение выигрывает)

1. `mode: off` → сквозной пропуск (аварийный рубильник)
2. `overrides.deny` → блок без вопроса
3. `overrides.allow` → пропуск молча
4. `tool_input.method` → по таблице HTTP-методов
5. `Bash` → глагол в URL, затем HTTP-метод из команды, затем `bash.confirm_patterns`;
   команда без URL и без совпадений проходит молча
6. Глагол из имени инструмента → `read` пропускаем, `mutate`/`destroy` спрашиваем
7. **Глагол неизвестен → спрашиваем**

Пункт 7 — сердце спеки. Новый MCP-сервер с незнакомым инструментом спрашивает, а не
проскакивает. Это делает гейт независимым от названия сервиса.

## Fail-closed

| Ситуация | Поведение |
|---|---|
| Политика не читается / не парсится | deny |
| Плагин недоступен | deny |
| Таймаут ожидания оператора (5 мин) | deny |
| Оператор нажал «Отклонить» | deny |
| Неизвестный глагол | **confirm**, не deny |

Отличие от `ask-user-question-hook.ts`, который намеренно fail-open (недоступен плагин →
нативный терминальный UI). Для изменяющих операций так нельзя.

## Область действия

**Под гейтом:** MCP-инструменты, не попавшие в `overrides.allow`; `Bash` с изменяющим
глаголом в URL, с изменяющим HTTP-методом или совпавший с `bash.confirm_patterns`.

**Вне гейта (`overrides.allow`):**
- `mcp__second_brain-*__*`, `mcp__gbrain-*__*` — собственная инфраструктура, решение оператора
- `mcp__firecrawl__*` — читающая утилита (см. выше)
- обычные команды `Bash` без URL и без совпадений — иначе агент встаёт на первой же команде

Бизнес-интеграции (1С, amoCRM, Bitrix24, Teamly, Yandex Tracker, Yandex Disk, HH.ru и
последующие) в `overrides.allow` не добавляются. Исключение для конкретного инструмента
такой интеграции — осознанное решение оператора под запись, а не настройка по умолчанию.

## Аварийный рубильник

Переменная окружения `CONFIRM_GATE=off`, читаемая хуком. Задаётся в окружении сессии
(systemd `EnvironmentFile` / wrapper запуска), требует рестарта агента. Агент не может её
переопределить для будущих вызовов хука: хуки наследуют окружение сессии, а `export` внутри
`Bash`-вызова живёт только в его подоболочке.

## Граница защиты

Гейт защищает от ошибок агента, а не от агента-противника. Агент имеет полный `Bash` и
технически может переписать файл политики. Смягчение: правки самого файла политики и
`settings.json` попадают в `bash.confirm_patterns`, то есть требуют подтверждения. Полной
защиты от намеренного обхода на этом уровне нет и быть не может.

Второй остаточный риск: инструмент с врущим именем (`get_report`, который внутри пишет).
Снаружи видно только имя и аргументы. Смягчение — карточка показывает аргументы целиком,
плюс точечные `overrides` по мере обнаружения.

## Не входит в объём

- Shadow-режим (оператор отказался — выкатываем сразу в enforce)
- Новые ограничения для `second_brain` / `gbrain`
- Оживление `permission_request` relay (остаётся как есть)
- Отказ от `--dangerously-skip-permissions`
