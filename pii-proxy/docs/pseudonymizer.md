# Сервис псевдонимизации (labops-pii)

> Код сервиса теперь в общей библиотеке `labops-pii` (вендорится в `vendor/labops-pii/`, модуль `labops_pii`; с 1.0.0 профилей нет, настройка только переменными окружения, см. `docs/MIGRATION.md` библиотеки). Собственных копий `pseudonymizer/` и `media-masker/` в репозитории нет; тесты и README библиотеки - в репозитории `labops-pii`. Ниже - описание поведения сервиса; имена модулей: `pseudonymizer.*` -> `labops_pii.*`, `media_masker.*` -> `labops_pii.media.mask.*`. Имена переменных окружения `PSEUDONYMIZER_*` и `MEDIA_MASKER_*` сохранены. Адреса (`ADDRESS`) маскируются при `PSEUDONYMIZER_ADDRESS_MASK=true` (его пишет `pii-setup.sh`).

Сервис псевдонимизации персональных данных (ПДн) в русском тексте. Заменяет ПДн токенами
вида `[PERSON_1]`, `[PHONE_2]`, `[EMAIL_1]` перед отправкой текста в модель и возвращает
оригиналы в ответе модели (`/restore`). Оригиналы хранятся только в таблице замен: по умолчанию
в памяти процесса (на диск не пишутся), опционально в зашифрованном SQLite.

Сервис общий: им пользуются `pii-proxy` агентов LabOps (память) и другие клиенты (например,
web-app v2, SQLite). Тред — это `<префикс>:<id сессии>`; префикс определяет ключи шифрования SQLite.

## Запуск

```bash
# Хост (venv, юниты, токены): bash agent-architecture/orchestration/pii-setup.sh host
# Вручную из корня монорепо:
python3.12 -m venv .venv
.venv/bin/pip install -r pii-proxy/deploy/labops-pii.requirements.txt \
  -c pii-proxy/deploy/labops-pii.constraints.txt
export PYTHONPATH="$PWD/vendor/labops-pii" PSEUDONYMIZER_ENABLE_DELETE_THREADS=on \
  PSEUDONYMIZER_ENABLE_EXPOSE_BOOT_ID=on PSEUDONYMIZER_ENABLE_CASE_LABELS=on
export PSEUDONYMIZER_API_TOKEN="$(.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(32))')"
.venv/bin/python -m labops_pii             # слушает 127.0.0.1:8300
```

Режим SQLite (`PSEUDONYMIZER_STORE=sqlite`) требует `PSEUDONYMIZER_KEY` (Fernet), его нужно
сгенерировать один раз (`python -c 'from cryptography.fernet import Fernet;
print(Fernet.generate_key().decode())'`) и хранить вне репозитория (потеряли ключ — таблица
нечитаема). Без ключа (или с невалидным) в этом режиме сервис не стартует (код выхода 1);
ключ молча не генерируется. В режиме памяти (по умолчанию) ключ не нужен. Сервис не стартует
без `PSEUDONYMIZER_API_TOKEN` ни в каком режиме.

## Аутентификация

`/pseudonymize`, `/pseudonymize_batch`, `/restore`, `/check` и `DELETE /threads/{id}` требуют заголовок `Authorization: Bearer <токен>`, где
токен равен переменной `PSEUDONYMIZER_API_TOKEN` сервиса (общий секрет с клиентом — локальным прокси `pii-proxy`). Сравнение
через `hmac.compare_digest`; без заголовка или с неверным токеном ответ 401 (проверка идёт
до разбора тела и до занятия слота), тихого отката нет. `/health` секрета не требует
(проверка живости для watchdog). Токен не пишется в журнал.

## Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `PSEUDONYMIZER_STORE` | `memory` (таблица в памяти процесса) или `sqlite` | `memory` |
| `PSEUDONYMIZER_KEY` | ключ Fernet; **обязателен только для `sqlite`** | — |
| `PSEUDONYMIZER_API_TOKEN` | общий секрет API (Bearer), **обязателен** | — |
| `PSEUDONYMIZER_RETENTION_HOURS` | через сколько часов без обращений тред удаляется из таблицы замен (0 — не удалять); проверка раз в 10 мин (память) / раз в час (SQLite) | `24` |
| `PSEUDONYMIZER_RETENTION_DAYS` | устаревшая: учитывается, только если нет `RETENTION_HOURS` (дни x 24) | — |
| `PSEUDONYMIZER_DB` | путь к SQLite-файлу таблицы замен | `data/pseudonymizer.sqlite3` |
| `PSEUDONYMIZER_MASK_LEGAL_ENTITY` | `true` — дополнительно маскировать НАЗВАНИЯ организаций (`ORG`); ИНН/ОГРН/счета маскируются всегда | `true` |
| `PSEUDONYMIZER_CONTACTS_FILE` | файл словаря контактов (строка = контакт, `#` — комментарий) | нет |
| `PSEUDONYMIZER_HOST` / `PSEUDONYMIZER_PORT` | адрес прослушивания | `127.0.0.1` / `8300` |
| `PSEUDONYMIZER_MAX_TEXT_CHARS` | предел длины текста в `/pseudonymize`, `/check` и `/restore` (422 выше) | `70000` |
| `PSEUDONYMIZER_MAX_RESTORE_TOKENS` | предел числа разных токенов `[TYPE_N]` в тексте для `/restore` (422 выше) | `5000` |
| `PSEUDONYMIZER_MAX_BATCH_ITEMS` | предел числа текстов в `/pseudonymize_batch` (413 выше) | `500` |

### Пределы и время

Клиент (`pii-proxy`) ждёт ответа 10 с (таймаут клиента), поэтому предел текста выведен из
замера худшего случая, а не взят с запасом «побольше». Замер 09.10.2026, 2 vCPU, 80 000
символов, время `/pseudonymize` (у `/check` то же без записи):

| Текст | мкс на символ | 80 000 символов |
|---|---|---|
| одни инициалы «А. Б. В. Г. » (худший найденный) | 80 | 6,4 с |
| телефоны и адреса почты подряд (5 000 новых токенов, база в памяти) | 63 | 5,1 с |
| пути и имена файлов | 55 | 4,4 с |
| плотный поток разных ФИО (2 400 новых токенов, база в файле) | 48 | 3,9 с |
| повтор плотного списка ФИО в треде (тот же текст вторым сообщением, база в файле; CPU, 16.10.2026) | 70 | 5,6 с |
| обычная проза | 16 | 1,3 с |

Умолчание 70 000 символов: худший случай 5,6 с, запас до таймаута 1,8 раза (константы
`WORST_SECONDS_PER_CHAR` и `WORST_CASE_TIMEOUT_SHARE` в `config.py`, сверка в тестах). Меньше
нельзя: клиент шлёт длинные результаты инструментов (до 60 000 символов) одним текстом. Запросы обрабатываются
потоками одного процесса, поэтому два худших запроса одновременно идут вдвое дольше и в
таймаут уже не укладываются; при такой нагрузке предел надо снижать либо поднимать таймаут.

Чтобы время было линейным по длине, запись токенов одного запроса фиксируется одним
коммитом (и отменяется целиком при сбое), а совместимые ФИО ищутся по индексу слов, а не
перебором всей таблицы треда: до правки 20 000 символов разных ФИО на базе в файле
обрабатывались 9,4 с, после 0,75 с. `/restore` читает все токены текста одним запросом к
таблице (пачками по 500) и расшифровывает только найденные: 80 000 символов и 2 400 токенов
за 0,05 с.

### Пакетное маскирование

Клиент маскирует результат инструмента по строковым листьям JSON (целиком нельзя: токен ломает
экранирование). Раньше каждый лист был отдельным `/pseudonymize`: результат поиска на 50
поставщиков (20 000 символов) - 433 вызова подряд (R9-A2-04). `/pseudonymize_batch` принимает
список текстов и обрабатывает их по одному, в порядке списка, ровно как серия одиночных
вызовов: тексты не склеиваются (соседний лист менял бы контекст NER), номера токенов и записи
таблицы замен те же (сверка в `tests/test_r9_batch.py` на `pii_corpus`, `recall_sets` и листьях
JSON результата поиска).

У текста пачки есть постоянная цена сверх длины: детект, леммы ФИО треда, коммит. Замер
16.10.2026, 2 vCPU под нагрузкой соседней сборки: короткий лист JSON (с NER) 5-6 мс, короткий
текст без ПДн 1,3 мс в пустом треде; в треде с ~850 ФИО до правки 10-18 мс, после неё 3-6 мс
(индекс ФИО треда строится только для текста, где найдено ФИО, а не для каждого). Поэтому
пачка ограничена «длиной с поправкой»: каждый текст, кроме первого, считается длиннее на
`BATCH_ITEM_COST_CHARS` = 100 символов (8 мс при 80 мкс на символ), и сумма не больше
`PSEUDONYMIZER_MAX_TEXT_CHARS`. Худшее время пачки то же, что у одного текста предельной
длины (5,6 с), пачка из одного текста проверяется ровно как `/pseudonymize`. Число текстов
ограничено `PSEUDONYMIZER_MAX_BATCH_ITEMS` (500: 4 с постоянной цены). Пачка сверх пределов -
413 (до обработки, ни одного токена не записано), слишком длинный текст в ней - 422, как у
одиночного.

Пачка занимает один слот конкуренции (`PSEUDONYMIZER_MAX_CONCURRENCY`, 2) на всё время
обработки: серия одиночных вызовов отпускала слот между листьями. Клиент поэтому шлёт пачки
не больше 100 текстов (около секунды слота): второй слот остаётся свободным, а ожидающий
запрос ждёт не дольше одной пачки (`BUSY_TIMEOUT_SECONDS` 4 с: вместе с худшей обработкой 5,6 с укладывается в таймаут клиента 10 с). Сервис без этого маршрута
отвечает 404, и клиент маскирует одиночными вызовами (порядок выкатки любой).

Разборы pymorphy и ключи ФИО запоминаются на время одного запроса (`morph.request_cache`,
его включает `detect`): общий LRU на 4 096 слов текст предельной длины (~16 600 разных
слов) вытеснял до повторного обращения. Повтор плотного списка ФИО в треде на 80 000
символов до правки занимал 11,3 с CPU (на 70 000 символов 9,9 с при таймауте клиента
10 с), после правки 5,6 с. Память запроса освобождается после ответа: пик процесса на этом
входе вырос на ~24 МиБ. Общий кэш на 65 536 слов ускорил бы повтор до ~1,8 с, но занял
бы ~150 МиБ навсегда.

## Что маскируется

| Тип токена | Что это |
|---|---|
| `PERSON` | ФИО (Natasha/Slovnet NER, в любом падеже, с инициалами); «ИП Фамилия И.О.», «ИП ПЕТРОВ ИВАН ИВАНОВИЧ» (капсом) целиком вместе с ИНН/ОГРНИП |
| `PHONE` | телефоны РФ/BY: `+7`, `8`, `+375`; международные с «+» и кодом страны (E.164, не меньше 9 цифр: `+86 138 0013 8000`, `+49 30 12345678`, `+86 13800138000`; код из 2 цифр и три группы по 3 - `+48 123 456 789`; ряды коротких групп при 10+ цифрах - `+33 6 12 34 56 78`, `+45 12 34 56 78`; префикс `00` вместо «+» принимается только с кодом страны из списка и разделителем - `0086 138 0013 8000`; без «+» и `00` не ищутся; суммы вида `+1 234 567 руб`, `12 345 678`, артикулы `123-456-789` телефоном не считаются); скобки, пробелы, дефисы; десять цифр с разделителями без префикса (`999 123 45 67`); десять цифр подряд - только после слова «тел», «моб», «phone» и т.п. (в той же строке или на следующей); слева допустимы буквы и `_` (`прайс_89991234567.xlsx`) |
| `EMAIL` | адреса электронной почты |
| `INN` | ИНН (10 цифр — организация, 12 — физлицо/ИП) с контрольной суммой или после слова «ИНН» (слово — с левой границей: «длинная» не считается); всегда |
| `OGRNIP` | ОГРНИП (15 цифр) с контрольной суммой или после слова «ОГРН»; всегда |
| `OGRN` | ОГРН (13 цифр): после слова «ОГРН» или с контрольной суммой и первой цифрой 1/5 (штрихкод EAN-13 не считается); всегда |
| `ACCOUNT` | расчётный/корреспондентский счёт (20 цифр, префикс 301/302/401-408/423/426); всегда |
| `SNILS` | СНИЛС: после слова «СНИЛС»; с разделителями и контрольной суммой; и всё, что похоже на СНИЛС по контрольной сумме, - 11 цифр подряд или группами `123-456-789 01` с верной контрольной суммой, даже без слова (правило одно на оба слоя, `find_snils_spans` в `shared/pii_patterns.py`). Около 1 % случайных 11-значных артикулов поэтому становятся токеном `[SNILS_n]` (восстанавливается в ответе); номер телефона с такой суммой остаётся `PHONE` |
| `PASSPORT` | серия и номер паспорта РФ |
| `CONTACT` | точное совпадение со словарём контактов (без учёта регистра); ник Telegram `@name` (латиница/цифры/`_`, 5-32 знака, не внутри адреса почты) и ссылки `t.me/…`, `telegram.me/…` |
| `ORG` | название организации (ООО/АО/ПАО… + название) — **только** при `PSEUDONYMIZER_MASK_LEGAL_ENTITY=true` |

Токены стабильны в пределах `thread_id`: одно значение — один токен на всех витках. Для ФИО
сопоставление идёт по лемме (pymorphy3): «Иванова» и «Иванову» — один токен; «Иванов И.» и
«Иванов Иван» объединяются, если кандидат однозначен. Слова ФИО, уже известные в треде,
маскируются и тогда, когда NER их пропустил.

Фамилия с двумя инициалами (R9-A4-12): «Петрова О.И.» и «О.И. Петрова» ловятся по морфологии и
без NER — Natasha пропускала фразы вроде «Заказ у Петрова О.И. оформлен.» целиком. Слово
считается фамилией, если у него есть разбор «фамилия» или его нет в словаре; словарные слова
(«Согласовано И.О.») и одна буква с точкой («П. 3») не срабатывают.

Пересечения находок (R9-A4-03): если находки делят хоть один символ, а важнейшая из них не
покрывает остальные, маскируется объединение диапазонов, открытым не остаётся ни один символ
(смежные находки не склеиваются). Запись словаря «Петров» в «Петров Иван Сергеевич» даёт один
токен `PERSON` на всё ФИО, тот же, что без словаря. Смесь ФИО и контактов - `PERSON` с ключом
ФИО; только контакты - `CONTACT`; другие смеси (контакт задел телефон) - тип важнейшей находки
и точный токен: общий только у того же написания, `/restore` возвращает фрагмент побайтно.

## API

Все тела — JSON. Оригиналы значений в ответах **не возвращаются**.

- `POST /pseudonymize` — `{"thread_id": "t1", "text": "позвони Петрову, +7 (902) 123-45-67"}` →
  `{"text": "позвони [PERSON_1], [PHONE_1]", "entities": [{"type": "PERSON", "token": "[PERSON_1]"}, {"type": "PHONE", "token": "[PHONE_1]"}]}`.
  `entities` — уникальные токены в порядке появления.
- `POST /pseudonymize_batch` — `{"thread_id": "t1", "texts": ["позвони Петрову", "", "petrov@firma.ru"]}` →
  `{"items": [{"text": "позвони [PERSON_1]", "entities": [...]}, {"text": "", "entities": []}, {"text": "[EMAIL_1]", "entities": [...]}]}`.
  Элемент ответа на каждый текст, в том же порядке; результат тот же, что у `/pseudonymize` по
  каждому тексту подряд. Пределы и время - «Пакетное маскирование».
- `case_labels` (необязательное `bool`, по умолчанию `false`; в телах `/pseudonymize` и
  `/pseudonymize_batch`). Без поля и при `false` ответ побайтно прежний. При `true` ФИО в
  косвенном падеже получает падежную метку: «Передай Кузнецову Олегу Игоревичу» →
  `"Передай [PERSON_1|datv]"`. Правила:
  - Только тип PERSON; именительный - без метки (не `|nomn`).
  - Падеж берётся по словам ФИО (pymorphy3): у каждого слова собираются падежи всех разборов
    с учётом рода (по отчеству/имени, как в `/restore`), берётся пересечение по словам.
    Инициалы и слова без разбора ФИО не учитываются.
  - Метка ставится, только если общий падеж ровно один и он не именительный. Неоднозначно -
    без метки: «Иванову» (муж. дат. / жен. вин.), «Иванова» (жен. им. / муж. род.),
    «Петрова О.И.», «Петровой Ольге» (дат. / предл.), «Кузнецова Олега» (род. / вин.). Нет
    общего падежа - тоже без метки.
  - Часть имени файла или пути метку не получает.
  - Нумерация и таблица замен те же, что без флага: «Кузнецову» и «Кузнецов» - один
    `[PERSON_1]`. `entities` всегда с голым токеном: `[PERSON_1]`.
  - Буквальные метки во входе по-прежнему экранируются; `/restore` и `/check` не меняются
    (`/check` метку находкой не считает).

  Примеры: «Кузнецову Олегу Игоревичу» → `[PERSON_1|datv]`; «Кузнецовым Олегом Игоревичем» →
  `[PERSON_1|ablt]`; «Кузнецов Олег Игоревич» → `[PERSON_1]`; «Позвони Иванову» →
  `Позвони [PERSON_1]`.
- `POST /restore` — `{"thread_id": "t1", "text": "Набери [PHONE_1]"}` → `{"text": "Набери +7 (902) 123-45-67"}`.
  Токены, которых нет в этом треде, остаются как есть. Текст длиннее предела или больше
  `PSEUDONYMIZER_MAX_RESTORE_TOKENS` разных токенов: 422.
- `POST /check` — `{"text": "..."}` → `{"has_pii": true, "types": ["EMAIL", "PERSON"]}`. Необязательный
  `thread_id` добавляет к проверке леммы ФИО этого треда: так текст, где токены уже заменены
  оригиналами (запрос внешнего инструмента), не пропускает одинокую фамилию «Сидоров арматура».
  Токены при проверке не создаются; без `thread_id` леммы не используются.
  Страховочная проверка перед отправкой наружу (вторая линия защиты клиента); ничего не сохраняет.
- `DELETE /threads/{thread_id}` — удаляет все замены треда (конец сессии клиента). `204`, и когда
  треда не было. После удаления токены этого треда `/restore` оставляет как есть, нумерация нового
  треда начинается с 1. Идентификатор без `/`.
- `GET /health` — `{"status": "ok", "boot_id": "<uuid4>"}` (без токена). `boot_id` новый на каждый
  запуск процесса: клиент по его смене узнаёт, что таблица в памяти потеряна, и перемаскирует
  историю заново.

### Падежные метки

Токен в ответе модели может нести падеж: `[PERSON_123456|ablt]`. Грамматика (согласована с
другим клиентом сервиса, менять нельзя):

- Регулярка метки: `\[([A-Z]+)_(\d+)(?:\|(nomn|gent|datv|accs|ablt|loct))?\]`. Код - одна граммема
  pymorphy строчной латиницей из закрытого набора; пробелов нет; максимум 20 символов
  (`[PERSON_123456|ablt]`).
- Метки пишет модель в ответе. `/pseudonymize` создаёт их только по `case_labels` (ниже); без
  поля во входе всегда простые `[TYPE_N]`.
- `/restore`:
  - PERSON с меткой - ФИО склоняется пословно (pymorphy3): фамилия, имя, отчество в нужный падеж;
    инициалы («И.», «И.И.») не меняются. Пол определяется по имени/отчеству, фамилия склоняется
    в том же роде. Слово, которое не склоняется или не разобрано, остаётся в исходной форме;
    регистр исходного слова сохраняется (Заглавная, КАПС); части через дефис склоняются каждая.
  - Метка у другого типа (PHONE, ORG, ...) игнорируется: подставляется оригинал как есть.
  - Номера нет в треде: фрагмент с меткой остаётся как есть (как неизвестные токены).
  - Код вне набора (`[PERSON_1|дат]`, `[PERSON_1|xyz]`) под регулярку не подходит: текст как есть.
  - Буквальная метка `[PERSON_1|datv]` во входе `/pseudonymize` экранируется тем же механизмом,
    что буквальные `[TYPE_N]`, и `/restore` её не трогает.
  - Предел `PSEUDONYMIZER_MAX_RESTORE_TOKENS` считает разные токены: метки одного токена с разными
    падежами - один токен.
- `/check`: метки не ПДн (как токены). Контракт ответа не меняется, меняется только текст.

Примеры (тред, где `[PERSON_1]` = «Петрова Ольга», `[PERSON_2]` = «Иванов Пётр Сергеевич»):

- `/restore` `"Передай [PERSON_1|datv]"` → `"Передай Петровой Ольге"`.
- `"Письмо от [PERSON_2|gent], копия [PERSON_2|ablt]"` → `"Письмо от Иванова Петра Сергеевича, копия Ивановым Петром Сергеевичем"`.
- `"Звони [PHONE_1|datv]"` → метка игнорируется, подставляется номер как есть.
- `"[PERSON_9|datv]"` (нет в треде) и `"[PERSON_1|дат]"` (код вне набора) → без изменений.

Четыре POST-метода и DELETE требуют `Authorization: Bearer <PSEUDONYMIZER_API_TOKEN>` (см. «Аутентификация»).
Цифры любых систем счисления (арабо-индийские, деванагари, полноширинные и т.д.) перед поиском
приводятся к ASCII, замена идёт по исходному тексту.

Ошибки валидации — `422` (пустой `thread_id`, нет поля).

Токен (`401`) и размер тела (`413`) проверяет ASGI-middleware до чтения тела: по
`Content-Length` и потоковым счётчиком байт. Предел тела выводится из
`PSEUDONYMIZER_MAX_TEXT_CHARS` и `PSEUDONYMIZER_MAX_BATCH_ITEMS` (12 байт JSON на символ
плюс запас), поэтому допустимый запрос он не режет.

## Хранилище

Интерфейс `ReplacementStore` (Protocol, `pseudonymizer/store.py`), две реализации:

- `MemoryReplacementStore` (по умолчанию) — словари в процессе под блокировкой, на диск ничего
  не пишется, оригиналы не шифруются. Перезапуск теряет таблицу (см. `boot_id`).
- `SqliteReplacementStore` — оригиналы и нормализованные ключи шифруются Fernet; для поиска по
  ключу HMAC-индекс. Ключи (Fernet и индекса) выводятся HKDF-SHA256 из мастер-ключа отдельно для
  каждого префикса треда (часть `thread_id` до первого `:`, нет двоеточия — весь id):
  `info = метка + "/" + префикс`. Схема помечена `v3` (шифртекст `v3:...`, индекс `v3:<hex>`);
  строки `v2` (общий ключ) и `v1` читаются как раньше. `python -m labops_pii.rekey` переводит
  только `v1` (на `v3`); `v2` остаются читаемыми и не трогаются. Привязки Bearer к префиксу нет:
  один токен на сервис.

Ретенция: тред без обращений (запись или `/restore`) дольше `PSEUDONYMIZER_RETENTION_HOURS`
(24; 0 — не удалять) удаляется целиком — в обеих реализациях. В SQLite даты в таблице
`thread_activity` (формат `replacements` и `rekey.py` не менялись, у старого файла даты
проставляются при первом запуске). Проверка при старте и далее из запросов `/pseudonymize*`:
не чаще раза в 10 минут для памяти и раза в час для SQLite.
Расшифрованные ключи `list_keys` в SQLite кэшируются по (тред, тип) в памяти процесса (до 256
пар), поэтому длинные треды не расшифровываются заново на каждом запросе.

## Логи

Одна запись - одна JSON-строка в stderr. Поля (белый список): `ts` (UTC, мс, `Z`), `level`
(`info`/`warning`/`error`/`critical`), `severity` (`info`/`warning`/`serious`/`critical`), `event`,
`service`, `trace_id` (32 hex из второго сегмента заголовка W3C `traceparent`; нет заголовка или он
невалиден - поля нет), `route` (ШАБЛОН маршрута, например `/v1/parse`; не найден - `unmatched`),
`status`, `duration_ms`, `code`, `exc_type`, `msg`.

События запроса (одно на запрос, после ответа): `http_request` (status < 400, severity `info`),
`http_request_rejected` (4xx, `warning`), `http_request_failed` (5xx и необработанное исключение,
`serious`; для исключения status=500). Также `service_started` / `service_stopped` (`info`).
Сбой `/restore` (5xx или исключение) пишется как `pseudonymizer_restore_failed` (`critical`) ВМЕСТО
`http_request_failed`, с полем `code` (тип исключения или `http_<status>`). Прочие записи `logging` идут с `event=log`: `msg` - шаблон сообщения до подстановки
аргументов, severity по уровню (ERROR/CRITICAL - `serious`, WARNING - `warning`, иначе `info`).
Таблица классов `EVENT_SEVERITY` в `pseudonymizer/jsonlog.py`.

Не пишется никогда: тексты запросов и ответов, тела, имена файлов, query-строка, фактический путь,
аргументы сообщений, текст и трассировка исключений (только тип `exc_type`). Access-лог uvicorn
отключён (`access_log=False`, `log_config=None`), логирует только middleware
(`pseudonymizer/jsonlog.py`, чистый ASGI: тело не читается и не буферизуется). Проверено тестами
`tests/test_jsonlog.py`.

## Ограничения качества

- Одиночные имена/фамилии в нижнем регистре («позвони петрову») NER не находит. ФИО ЗАГЛАВНЫМИ и строчными (2-3 слова подряд или фамилия с инициалами: `ИВАНОВ ИВАН ИВАНОВИЧ`, `иванов и.и.`) ловит отдельное правило по морфологии: каждое слово - одушевлённая фамилия/имя/отчество по главному разбору pymorphy, сочетание «фамилия + имя/отчество/инициалы» или «имя + отчество»; одиночные слова и пары вроде `РОМАШКА ТРЕЙД` не маскируются.
- Первая встреча одиночной фамилии в начале фразы без контекста может быть пропущена
  (повторные встречи в треде ловятся по лемме).
- Кличка/ник и одиночные латинские имена («Rustam») не находятся; для них — словарь контактов.
  Латинское ФИО из 2-3 слов находится после метки контакта (`Contact:`, `Attn:`,
  `Manager:`, `Best regards,`); слова вроде `Department`, `Office`, `Team`, `Please`, `Sheet`
  имя не образуют. После такой находки в том же тексте маскируются и повторы: полная форма
  (`John Smith`) и каждое слово имени от 3 букв (`Smith`) с точным регистром и границами слова;
  `Smithson`, `blacksmith`, `smith` не затрагиваются. В следующих запросах треда имя
  уже известно и ловится по лемме. Если метки рядом нет, первое появление латинского ФИО
  остаётся открытым; без метки контакта латинские ФИО не находятся, в
  частности: `Li Wei, +86 …`, `SMITH JOHN`, `Mr. John Smith`, `Smith, John`, `McDonald`,
  `O'Brien`. Для них нужен словарь контактов. Слова имени из 1-2 букв (`Li`) отдельно не ищутся.
- ИНН (10 и 12 цифр) маскируется всегда (по контрольной сумме или после слова «ИНН»); флаг
  `PSEUDONYMIZER_MASK_LEGAL_ENTITY` управляет только названиями организаций (`ORG`).
- При разных формах одного ФИО в одном тексте `/restore` возвращает форму, встретившуюся
  первой (падеж не восстанавливается).
- Имена файлов (`*.xlsx`, `*.docx`, `*.pdf`…), пути и слова через «_» NER на ФИО не проверяются
  (границы замены — по токену текста, не по лемме): `Металлопрокат_прайс.xlsx` остаётся как есть.
  Отдельно каждая кириллическая часть имени файла проверяется правилом по словарю
  (`_detect_tech_names`): ФИО, вшитое в имя файла (`Иванов_договор.docx`), маскируется
  (заменяется само слово, разделители остаются). Словарные неодушевлённые существительные
  («Металлопрокат», «Сибирь») за ФИО не считаются.
- Склонение по метке `[PERSON_N|падеж]` идёт по словарю pymorphy: редкие и несловарные фамилии
  могут не склониться (остаются в исходной форме), несклоняемые (Шевченко, Дюма) не меняются;
  род берётся по отчеству или имени; без них — по фамилии, только если она однозначна по роду
  («Сидоров» склоняется). Неоднозначная («Иванова», «Петрова О.И.» — она или его родительный)
  возвращается как есть: ошибка рода хуже несклонённого ФИО.
- Инвариант `restore(pseudonymize(x)) == x` строг для одной формы ФИО в треде; разные формы
  одного человека делят токен (см. выше).
- Обработка потокобезопасна внутри одного процесса; несколько воркеров с одним SQLite-файлом
  не рассчитаны.
- Natasha тянет `pkg_resources` — поэтому в зависимостях `setuptools<81`.

## Ключи и перешифрование

Из `PSEUDONYMIZER_KEY` выводятся два независимых ключа через HKDF-SHA256 (метки info
`pseudonymizer/replacements/fernet/v2` и `.../index-hmac/v2`): один для Fernet, другой для
слепого индекса (S-02). Новые строки пишутся схемой v2 (шифртекст с префиксом `v2:`, индекс
`v2:<hex>`); строки старой схемы (один ключ на всё) читаются как раньше. Перевод старых строк:
`python -m labops_pii.rekey --dry-run`, затем без `--dry-run` (порядок действий и бэкап в
`docs/RUNBOOK.md`, раздел «Перешифрование таблицы замен»). Ключ проверяется пробной
расшифровкой всех строк до создания копии: с неверным ключом копия не появляется. Файл копии
создаётся сразу с правами 600 (`O_EXCL`, существующий файл не перезаписывается), при сбое
копирования недописанный файл удаляется.
