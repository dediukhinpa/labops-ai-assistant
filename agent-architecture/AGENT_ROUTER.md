# Agent routing: как агенты передают работу друг другу

Документ про маршрутизацию задач между агентами LabOps. Путей **два**, и важно их
не путать:

| Путь | Механизм | Стоимость | Когда |
|------|----------|-----------|-------|
| **Доска + опрос** (дефолт) | задача на доске `task_mcp` (:5003), получатель опрашивает `task-poller.sh` | бесплатно (подписка) | вся рутина |
| **MCP-пуш** (резерв) | `agent_router.notify` (MCP :5000) → `webhook-listener` | **SDK-кредиты** (доставка через headless `claude -p`) | только срочное «разбуди сейчас» (инцидент, блокирующий handoff) |

> **Важно:** дефолтный путь **сознательно НЕ использует MCP `agent_router`** — тот
> доставляет через `claude -p`, а это отдельные кредиты мимо подписки. Имя
> `agent_router` относится к пуш-пути из нижней строки таблицы, не к опросу.

## Канал задач: доска `task_mcp`

Задача — это запись на доске с **изменяемым состоянием**, а не заметка в памяти.
Разница принципиальная и стоила нам инцидента, см. «Почему не заметки» ниже.

### Отправитель ставит задачу

```
task_create(title="починить парсер тендеров",
            description="<что сделать, критерии готовности>",
            assignee="carmella",
            priority="high")            # low | medium | high | critical
→ {"id": 42, "status": "new", ...}
```

`assignee` — кому. Без него задача ложится в общую очередь, и её заберёт первый,
кто вызовет `task_claim()` без аргументов.

### Получатель забирает и ведёт задачу

Поллер сам увидит `status: new` на ваше имя и вбросит в сессию строку с номером.
Дальше — состояния, и переходы **строго** по машине:

```
task_claim(task_id=42)      # new      → progress, атомарно, с лизом
   ...работа ФОНОВЫМ субагентом...
task_review(task_id=42)     # progress → review
task_done(task_id=42)       # review   → done   (терминальное)
```

- **`progress → done` напрямую запрещён.** Закрытие только через `review`, иначе
  прилетит `invalid transition` и задача зависнет в работе.
- Упёрлись — `task_block(task_id, reason=...)` (из `new` или `progress`).
  Разблокировка — `task_reopen` (`blocked → new`, `review → progress`).
- `task_claim` атомарен: два агента одновременно никогда не получат одну задачу.
  Лиз позволяет супервизору вернуть задачу в очередь, если исполнитель умер.

### Отправитель проверяет исполнение

```
task_list(assignee="carmella", status="done")
task_get(task_id=42)
task_history(task_id=42)     # кто и когда менял статус
```

### Границы доски

- **Скоуп.** Писать на доску (`task_create`, `task_claim`, `task_*`) может только
  агент с `task-board` в `can_write_scopes`. Чтение — всем.
- **Задержка, а не мгновенность.** Получатель узнаёт о задаче на ближайшем цикле
  опроса, не в ту же секунду. Для срочного — `agent_router` (см. выше).
- **Уникальность.** Дублей по заголовку доска не склеивает — это записи с id, а
  не заметки с content-hash. Одинаковые заголовки допустимы, но не помогают.

## Почему не заметки (и что делать со старыми)

Раньше задачи ставились decision-заметкой с конвенцией `TASK-FOR: <agent>` /
`STATUS: open` в теле. Так делать больше **не надо**. Причина:

Vault неизменяем по замыслу. Закрыть задачу-заметку можно было только
`supersede_decision` — а это пишет **новую** заметку, оригинал навсегда остаётся
`STATUS: open`. То есть каждая задача занимала **два слота** в окне опроса
(`recent(limit=30)`) и не освобождала их никогда: ёмкость — 15 задач за всю
историю роя, после чего задачи начали бы теряться молча. На 02.09.2026 было
израсходовано 6 слотов из 30, и все три «открытые» задачи в окне на деле были
закрыты — их держал только локальный `.task-seen` каждого агента.

У доски состояние настоящее: закрытая задача уходит из выборки. Очередь
ограничена числом **одновременно** открытых задач, а не всех задач за историю.
Плюс фильтр по `assignee` и `status` идёт в SQL — окна, которое можно
переполнить посторонними записями, нет в принципе.

**Переходный период.** Поллер читает **оба** канала: сначала доску, потом старое
окно заметок. Старые задачи доработают, новые ставьте только через `task_create`.
Поллер теперь понимает и `supersede`: задача, на которую ссылается заметка-преемник
(`Supersedes [[...]]`), закрытой считается по-настоящему, а не только по
`.task-seen`.

## Циклы опроса

Доставку ведёт `agent-template/scripts/task-poller.sh` — тонкий bash-надзор, под
ним постоянный python-процесс `task_poller.py` (одно HTTP-соединение и одна живая
MCP-сессия на каждый из двух источников). Запускается из `start-agent.sh`
(`setsid`, переживает выход start-agent; guard от дублей; сам выходит, когда
сессия умерла), надзирается watchdog'ом.

Ключевой приём — **развести дешёвый опрос и дорогой вброс**:

- **Опрос** каждые `TASK_POLL_INTERVAL` с (по умолч. **5**) — HTTP-вызовы
  `task_list` и `recent`. Агента они НЕ будят, стоят ~9 мс и ~0.3% ядра.
- **Вброс** в сессию — только когда появилась *новая* задача на моё имя И сессия
  на **чистом idle-промпте** (тот же детект, что у watchdog). Печатаем одну
  строку через `tmux send-keys -l`; инструкция велит выполнять задачу **фоновым
  субагентом**, чтобы длинная работа не занимала основную сессию.
- **Идемпотентность**: доставленное пишется в `core/active/.task-seen`
  (`task:<id>` для доски, путь заметки для наследия) и повторно не вбрасывается,
  в т.ч. через рестарты поллера.
- **Занят** (активный turn / застрявший ввод) → доставку откладываем, задача
  остаётся неотмеченной и уедет на ближайшем чистом промпте. В активную
  генерацию не печатаем.
- **Изоляция каналов**: упавшая доска не мешает заметкам и наоборот — сбой
  каждого источника логируется и не роняет проход.

| Точка | Интервал | Источник |
|-------|----------|----------|
| task-poller | `TASK_POLL_INTERVAL` с (по умолч. **5**) | `task-poller.sh` → `task_poller.py`, запуск из `start-agent.sh` |
| session-start | при каждом старте | хук session-start (сканирует inbox) |
| idle-консолидация памяти | `MEMORY_IDLE_CONSOLIDATE_MIN` мин | watchdog → `reflect-nudge` (это про память, не про задачи) |

Задержка доставки для простаивающего получателя ≈ `TASK_POLL_INTERVAL`. Всё внутри
подписочной сессии — **ноль SDK-кредитов**. Настоящий отдельный процесс на задачу
(истинный параллелизм) потребовал бы `claude -p` = SDK-кредиты, поэтому не делаем.

## Проверка (round-trip)

```
# отправитель
task_create(title="smoke", description="ничего не делать, просто закрыть",
            assignee="carmella")                      → id
# получатель (поллер доставит сам; вручную — так же):
task_list(assignee="carmella", status="new")          # задача видна
task_claim(task_id=<id>) ; task_review(task_id=<id>) ; task_done(task_id=<id>)
# отправитель
task_get(task_id=<id>)                                # status: done
task_history(task_id=<id>)                            # кто и когда менял
```
