# Agent routing: как агенты передают работу друг другу

Документ про маршрутизацию задач между агентами LabOps. Есть **два** пути, и важно
их не путать:

| Путь | Механизм | Стоимость | Когда |
|------|----------|-----------|-------|
| **Память + опрос** (дефолт) | задача в общей L4-памяти (`decisions`), получатель опрашивает `task-poller.sh` | бесплатно (подписка) | вся рутина |
| **MCP-пуш** (резерв) | `agent_router.notify` (MCP :5000) → `webhook-listener` | **SDK-кредиты** (доставка через headless `claude -p`) | только срочное «разбуди сейчас» (инцидент, блокирующий handoff) |

> **Важно:** дефолтный путь **сознательно НЕ использует MCP `agent_router`** — тот
> доставляет через `claude -p`, а это отдельные кредиты мимо подписки. Маршрутизация
> здесь realized через общую память. Имя MCP `agent_router` относится к пуш-пути из
> нижней строки таблицы, не к опросу.

Дефолт проверен end-to-end (2026-07-20: developer пишет → carmella читает своим
токеном → выполняет → закрывает, PASS). Дальше — про него.

## Канал задач: decision-note с конвенцией

`create_handoff` пишет в `inbox/{from}-to-{to}-{дата}.md` — путь фиксирован по дате,
**второй хэндоф за день перезаписывает первый**. Поэтому как основной канал он не
годится (теряет задачи). Основной канал — **decision-note** с конвенцией в заголовке
и тегах: scope `decisions` доказанно пишется отправителем и читается получателем.

### Отправитель ставит задачу

Инструмент `create_decision_note` (memory-mcp :5001):

```
title: "[TASK→carmella] <краткая суть>"
body:  "TASK-FOR: carmella\nSTATUS: open\n\n<что сделать, критерии готовности>\n\n[[<связанные>]]"
tags:  ["task", "task-for-carmella", "status-open"]
agent: "developer"
```

**Важно — адресация и статус живут в ТЕЛЕ, машиночитаемо (первые строки):**

```
TASK-FOR: <agent>
STATUS: open
```

Причина: `recent()` возвращает **тело** заметки как `snippet`, но **не** frontmatter-теги
и **не** title. Поэтому поллер (см. ниже) распознаёт задачу по строкам `TASK-FOR:` и
`STATUS:` в теле. Теги (`task-for-<agent>`, `status-open`) оставляем для человека и
recall, но опрос на них НЕ опирается — их в выдаче recent() нет.

- Заголовок должен быть уникален (иначе upsert по content-hash склеит записи) —
  добавляйте суть/тикет, не только `[TASK→carmella]`.

### Получатель забирает задачи (поллер, на каждом цикле опроса)

Поллер `task-poller.sh` каждые ~5с зовёт `recent(scope="decisions")` и берёт записи,
у которых в теле `TASK-FOR: <me>` и `STATUS: open`, ещё не отмеченные в `.task-seen`.
Забрав, читает полную заметку `memory_router.get(path)`, выполняет **фоновым
субагентом**, затем **меняет статус**:

- `supersede_decision(old_path, new_title, new_body="STATUS: done ...", reason="...")`
  — переводит задачу в done, сохраняя связь со старой версией; **или**
- новый decision-note `[ACK→developer] <суть>` с `status-done` — квитанция обратно
  отправителю тем же механизмом.

### Отправитель проверяет исполнение

На своём цикле опроса делает `recall("[ACK→developer]")` / `recent(decisions)` и
видит закрытые задачи. Круг замкнут — без единого платного вызова.

## Циклы опроса

Доставку задач ведёт `orchestration/../agent-template/scripts/task-poller.sh` —
отдельный лёгкий цикл на агента, запускаемый из `start-agent.sh` (`setsid`,
переживает выход start-agent; guard от дублей; сам выходит, когда сессия умерла).

Ключевой приём — **развести дешёвый опрос и дорогой вброс**:

- **Опрос** каждые `TASK_POLL_INTERVAL` с (по умолч. **5**) — это HTTP `recent`
  к memory_router. Он агента НЕ будит, стоит копейки, поэтому 5с не проблема.
- **Вброс** в сессию — только когда появилась *новая* задача на моё имя И сессия
  на **чистом idle-промпте** (тот же детект, что у watchdog). Печатаем одну строку
  через `tmux send-keys -l` (примитив watchdog), инструкция велит выполнить задачу
  **фоновым субагентом** — длинная задача не занимает основную сессию.
- **Идемпотентность**: каждый доставленный путь пишется в `core/active/.task-seen`
  и повторно не вбрасывается, в т.ч. через рестарты поллера.
- **Занят** (активный turn / застрявший ввод) → доставку откладываем, задача
  остаётся «непрочитанной» и уедет на ближайшем чистом промпте. В активную
  генерацию не печатаем.

| Точка | Интервал | Источник |
|-------|----------|----------|
| task-poller | `TASK_POLL_INTERVAL` с (по умолч. **5**) | `task-poller.sh`, запуск из `start-agent.sh` |
| session-start | при каждом старте | хук session-start (сканирует inbox) |
| idle-консолидация памяти | `MEMORY_IDLE_CONSOLIDATE_MIN` мин | watchdog → `reflect-nudge` (это про память, не про задачи) |

Задержка доставки для простаивающего получателя ≈ `TASK_POLL_INTERVAL`. Всё внутри
подписочной сессии — **ноль SDK-кредитов**. Настоящий отдельный процесс на задачу
(истинный параллелизм) потребовал бы `claude -p` = SDK-кредиты, поэтому не делаем.

## Проверка (round-trip)

```
# отправитель
create_decision_note(title="[TASK→carmella] smoke",
                     body="TASK-FOR: carmella\nSTATUS: open\n\n<...>",
                     tags=["task","task-for-carmella","status-open"], agent="developer")
# получатель (поллер доставит автоматически; вручную — так же):
recent(scope="decisions")            # запись видна, в теле TASK-FOR: carmella / STATUS: open
get(path=...)                        # прочитать полную задачу
supersede_decision(old_path=..., new_body="TASK-FOR: carmella\nSTATUS: done\n\n<...>",
                   reason="smoke ok")
# отправитель
recall(query="[TASK→carmella] smoke done")   # видит закрытие
```

## Границы

- **Задержка, а не мгновенность.** Получатель узнаёт о задаче на ближайшем цикле, не в
  ту же секунду. Для срочного — отдельный путь через `agent_router` (см. выше).
- **Scopes.** Отправитель должен иметь `decisions` в `can_write_scopes`, получатель —
  в `can_read_scopes` (проверяется tool-gating; developer/carmella — OK).
- **Идемпотентность.** Уникальный заголовок задачи обязателен, иначе upsert по
  content-hash склеит разные задачи в одну запись.
